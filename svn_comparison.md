# Git vs SVN: сравнение

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это всего лишь **указатель на коммит** (файл размером 41 байт со ссылкой на SHA-1 хеш). Создание ветки не копирует файлы и не занимает места — это мгновенная операция, которая просто записывает новый указатель. История при этом остаётся общей, а переключение между ветками (checkout) происходит локально и быстро.

В SVN ветка — это **физическая копия директории** внутри репозитория (`svn copy`). Она создаёт новое дерево файлов на сервере, что требует времени, дискового пространства и сетевого взаимодействия. Чем больше проект — тем дороже операция. Именно поэтому в SVN-проектах ветками пользуются редко, а в Git — постоянно (feature-ветки, hotfix, release).

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, нельзя.** SVN — централизованная система: вся история хранится на одном сервере, а рабочая копия на клиенте содержит только последнюю версию файлов (плюс скрытые `.svn`-директории с метаданными). Коммит — это операция, которая отправляет изменения **на сервер**, поэтому без сети она невозможна.

Офлайн в SVN можно только:
- редактировать файлы;
- смотреть diff с базовой ревизией;
- откатывать незакоммиченные правки (`svn revert`).

Всё, что касается истории — `svn log`, `svn blame`, коммит — требует подключения.

Для сравнения: в Git коммит полностью локален. Вы фиксируете изменения в **своей** копии репозитория, и только `git push` требует сети.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

1. **Legacy-проекты и госсектор/банки.** Если система 10–15 лет работает на SVN и в ней сотни тысяч строк кода, миграция на Git стоит дорого и рискованно. Проще поддерживать существующее.

2. **Очень большие бинарные файлы.** SVN лучше работает с бинарниками (графика, CAD, видео), потому что хранит не полную историю всех версий локально, а только рабочую копию. Git же при клонировании тянет всю историю, что для больших бинарников превращается в гигабайты (решается Git LFS, но это доп. настройка).

3. **Жёсткий централизованный контроль доступа.** В SVN можно раздать права на отдельные директории внутри одного репозитория. В Git права настраиваются на уровне репозитория целиком, а тонкая нарезка прав требует дополнительных инструментов (Gitolite, GitLab-группы).

4. **Команды с низкой квалификацией в Git.** Если разработчики привыкли к линейной модели «обновил → закоммитил», SVN-модель проще для понимания, чем ветвление в Git.

5. **Простая модель релизов без параллельных веток.** Когда проект не требует feature-веток и hotfix-веток, а идёт линейно — SVN справляется без накладных расходов.
